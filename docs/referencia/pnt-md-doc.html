WebBroker Market Data · WB_MD

Manual de Integração

O WebBroker Market Data (WB_MD) é um servidor de distribuição de dados de mercado em tempo real. Ele recebe os dados dos servidores feeder da PnT via TCP (protobuf) e os distribui a clientes web através de um único hub SignalR (/mdhub) sobre WebSocket.

Por esse hub o cliente recebe: book de ofertas (completo e agregado, com profundidade configurável), trades, ticker, preço de fechamento, bandas de preço, status do papel, metadados de instrumentos (SecurityInfo), lista de opções de um subjacente (OptionList) e velas OHLC.

🗂️
Este manual documenta dois serviços da Plug n' Trade: o WebBroker Market Data (WB_MD), apresentado nesta primeira parte, e o WB Strategy Robot — hub para envio, modificação, cancelamento e acompanhamento de estratégias/ordens algorítmicas. Para ir direto ao segundo serviço, veja o capítulo Strategy Robot — Envio de Estratégias.
Hub WB_MD Transporte WebSocket Auth OAuth2 Bearer (JWT) Serialização Newtonsoft JSON / MessagePack
⚠️
Ambiente de homologação (HML). Os endpoints deste manual — deste capítulo (WB_MD) e do capítulo Strategy Robot — apontam para o ambiente de homologação: Authorization Server https://auth-hml.pnt.api.br e hub https://webbrokermdhml.pnt.api.br/mdhub.

Arquitetura — visão de alto nível

O cliente autentica-se no Authorization Server, obtém um JWT e conecta-se ao hub WB_MD via SignalR + WebSocket. O WB_MD, por sua vez, consome os dados dos servidores feeder da PnT por TCP/ProtoBuf.

HubPara quê serveURL
WB_MD Book de ofertas, trades, ticker, price band, status, metadados, lista de opções e velas OHLC https://webbrokermdhml.pnt.api.br/mdhub
ℹ️
O hub usa WebSocket como transporte (HTTP long-polling não é suportado), exige OAuth2 Bearer (JWT) e suporta os protocolos de serialização Newtonsoft JSON e MessagePack.

Autenticação

A autenticação é feita via OAuth2 + OpenID Connect. O cliente obtém um access token (JWT) e o utiliza na conexão SignalR. Há dois fluxos: client_credentials (serviço-a-serviço) e authorization_code + PKCE (usuário interativo).

Descoberta OpenID

Antes de qualquer outro passo, faça um GET ao discovery endpoint para obter os endpoints reais (token, autorização, revogação):

HTTP
GET https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/.well-known/openid-configuration

A resposta é um JSON contendo, entre outros campos:

JSON
{
  "issuer": "https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider",
  "authorization_endpoint": "https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/authorize",
  "token_endpoint": "https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/token",
  "revocation_endpoint": "https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/revocation",
  "jwks_uri": "...",
  "scopes_supported": [ "robot_signalr_api", "pntdata_live_scope", "ohlc_subscriber", "..." ]
}
💡
Faça o discovery uma única vez na inicialização do cliente e armazene em cache. Os endpoints raramente mudam.

Fluxo Client Credentials (serviço-a-serviço)

Usado quando não há um usuário humano interativo — um robô de coleta, um servidor de back-office, um conector institucional. Requer apenas client_id + client_secret.

📤 Requisição

HTTP
POST https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/token
Content-Type: application/x-www-form-urlencoded
Authorization: Basic base64(client_id:client_secret)

grant_type=client_credentials
ℹ️
Não é necessário enviar &scope neste fluxo. O Identity Server carrega automaticamente todos os escopos autorizados do cliente a partir do banco de dados e os inclui no token emitido.

📥 Resposta (200 OK)

JSON
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",
  "token_type":   "Bearer",
  "expires_in":   3600,
  "scope":        "pntdata_live_scope ohlc_subscriber"
}

O access_token é um JWT que vale por expires_in segundos (tipicamente 1 hora).

💡
É no fluxo client_credentials que o Authorization Server pode inserir o claim pnt_plan (e os correlatos pnt_symbols, pnt_book, pnt_tick, pnt_market), a partir do plano contratado no banco. Esse conjunto de claims determina os limites de acesso descritos em Controle de Acesso.

Authorization Code + PKCE (usuário interativo)

Usado quando um usuário humano está operando — uma aplicação web ou desktop em que o cliente faz login com as próprias credenciais.

Etapa 1 — Redirecionar o navegador para o endpoint de autorização

HTTP
GET https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/authorize
    ?response_type=code
    &client_id=<seu_client_id>
    &redirect_uri=<sua_url_de_callback>
    &scope=pntdata_live_scope ohlc_subscriber openid
    &state=<string_aleatória_anti_csrf>
    &code_challenge=<base64url(sha256(code_verifier))>
    &code_challenge_method=S256
    &nonce=<string_aleatória>

O usuário faz login na tela do servidor de autorização e é redirecionado de volta para redirect_uri com ?code=...&state=....

ℹ️
Para efetuar o login o usuário precisará de um usuário e senha fornecidos pela PnT.

Etapa 2 — Trocar o code por um token (📤)

HTTP
POST https://auth-hml.pnt.api.br/PnTAuthorizationServerProvider/connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&client_id=<seu_client_id>
&redirect_uri=<sua_url_de_callback>
&code=<código_recebido_no_redirect>
&code_verifier=<o_code_verifier_original>

📥 Resposta (200 OK)

JSON
{
  "access_token":  "eyJhbGciOiJSUzI1NiIs...",
  "refresh_token": "...",
  "token_type":    "Bearer",
  "expires_in":    3600,
  "id_token":      "...",
  "scope":         "pntdata_live_scope ohlc_subscriber openid"
}
⚠️
Sempre use PKCE (code_challenge + code_verifier) em qualquer cliente, mesmo backend. É obrigatório no servidor da Plug n' Trade.
💡
Tokens obtidos por authorization_code normalmente não carregam o claim pnt_plan — nesse caso o cliente opera pelo caminho legado (ilimitado), descrito em Fluxo Legado.

Como passar o token ao SignalR

No hub de Market Data, o token é extraído do parâmetro access_token da query string:

URL
wss://webbrokermdhml.pnt.api.br/mdhub?access_token=<JWT>

A maioria das bibliotecas SignalR oferece um factory para fornecer o token dinamicamente:

JavaScript
import { HubConnectionBuilder } from "@microsoft/signalr";

const md = new HubConnectionBuilder()
  .withUrl("https://webbrokermdhml.pnt.api.br/mdhub", {
    accessTokenFactory: () => acquireFreshToken(),  // sua função
    skipNegotiation: false,
    transport: 1  // WebSockets
  })
  .withAutomaticReconnect()
  .build();
💡
O accessTokenFactory é chamado a cada conexão e a cada reconexão. Isso permite renovar o token sem recriar o objeto de conexão.

Renovação e revogação

Renovação (refresh)

HTTP
POST <token_endpoint>
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token
&refresh_token=<refresh_token>
&client_id=<seu_client_id>
⚠️
O fluxo client_credentials não retorna refresh_token. Nesse caso, basta solicitar um novo access_token quando o atual estiver perto de expirar.
💡
Estratégia recomendada: renove o token antes de expirar (ex.: a cada 50 min se expires_in=3600). A reconexão automática do SignalR pegará o token novo via accessTokenFactory.

Controle de Acesso por Cliente — Planos e Claims

🆕
Principal novidade do WB_MD. O acesso aos dados passou a ser regido por um plano por cliente, dirigido por claims que o Authorization Server preenche a partir do banco. O WB_MD apenas lê e aplica essas claims — ele não as calcula.

Regra mestre (retrocompatível)

Tudo gira em torno da presença ou ausência do claim pnt_plan no JWT:

Situação do tokenComportamento
Sem o claim pnt_planCaminho legado (ilimitado) — idêntico ao comportamento anterior. Nada muda para os clientes existentes.
Com o claim pnt_planAs regras de negócio dirigidas por claims passam a valer.
⚠️
Essa regra garante retrocompatibilidade total: clientes cujo token não carrega pnt_plan — o que inclui a maioria dos fluxos authorization_code e os client_credentials sem plano contratado — continuam operando sem qualquer alteração e sem limites.
💡
Existe um interruptor mestre de servidor (Entitlements:Enabled no appsettings.json). Se false, o servidor força o caminho legado para todos, ignorando quaisquer claims de plano. O padrão é true.

Fluxo sem pnt_plan — ilimitado (legado)

Aplica-se a qualquer token sem o claim pnt_plan, independentemente do grant type. O que o cliente pode fazer:

CapacidadeDetalhe
TópicosSubscrever qualquer tópico (Book, AggrBook, Ticker, LastTrade, ClosingPrice, PriceBand, SecurityStatus, SecurityInfo, OptionList).
SímbolosQualquer quantidade de símbolos simultaneamente (sem limite).
ProfundidadeBook na profundidade máxima configurada no lado da API (servidor).
MercadosAtivos de qualquer mercado (bvsp/bvmf).
Fluxo passo a passo
1. POST /connect/token  (grant_type=client_credentials OU authorization_code)
   → access_token SEM claim pnt_plan
2. Conecta ao /mdhub com o token
3. SubscribeMarketData(requestId, asset, topic)  → aceito, sem checagem de plano
4. Recebe OnUpdateMarketData(asset, topic, payload)  → book completo

Neste caminho, o servidor chama diretamente a rotina de subscrição legada. Nenhuma das mensagens de erro de plano (Ticker is not allowed..., Symbol limit reached...) pode ocorrer.

Fluxo com pnt_plan — dirigido por claims

Aplica-se a tokens client_credentials cujo cliente possui um plano contratado. O Authorization Server insere os seguintes claims:

Tabela 1 — Claims de plano

ClaimTipoSignificado
pnt_planstringIdentificador do plano (ex.: advanced-ambos, advanced-bvsp, lite-bvmf). Sua presença ativa as regras.
pnt_symbolsintLimite concorrente de símbolos distintos subscritos ao mesmo tempo. Ausente/inválido = ilimitado.
pnt_bookintPolítica de profundidade: 2 = book completo, 1 = apenas topo de book (1 nível).
pnt_tickstring"true" permite dados de trade (LastTrade/LastTradePrice); qualquer outro valor nega.
pnt_marketstring (repetível)Mercado(s) permitido(s): bvsp e/ou bvmf. O token pode trazer o claim mais de uma vez — os valores são unidos num conjunto.
⚠️
Ticker é um caso especial: só é permitido no plano advanced-ambos. Nenhum outro plano recebe Ticker, mesmo com pnt_tick=true.

Como as claims viram permissões

O servidor faz o parse das claims uma única vez por conexão e memoiza o resultado (nunca reprocessa por mensagem):

Regra derivadaOrigem
Máx. de símbolos concorrentespnt_symbols. Book + AggrBook + Ticker do mesmo papel contam como 1 (a chave é o ativo). Ao dessubscrever, a vaga é liberada.
Política de bookpnt_book: 2 → book completo, 1 → só topo (1 bid + 1 offer).
Trades permitidos?pnt_tick == "true".
Ticker permitido?Somente se pnt_plan == "advanced-ambos".
Mercados permitidosConjunto (união) de todos os pnt_market. Conjunto vazio = sem restrição de mercado.

Tabela 2 — Exemplos de planos

pnt_planSímbolosBookTradesTickerMercados

advanced-bvspconforme pnt_symbolscompleto (2)simnãobvsp

⚠️
Trades liberados em todos os planos. O claim pnt_tick vem como true para qualquer plano — dados de trade (LastTrade/LastTradePrice) são liberados para qualquer plano, inclusive os lite. O que diferencia os planos é a profundidade de book (pnt_book), o Ticker (só advanced-ambos), os mercados (pnt_market) e o limite de símbolos (pnt_symbols).
💡
A tabela é ilustrativa da convenção de nomenclatura (<tier>-<mercado>). Os valores efetivos vêm sempre das claims individuais (pnt_book, pnt_tick, pnt_market, pnt_symbols), não do nome — exceto Ticker, que depende do nome do plano ser exatamente advanced-ambos.

Fluxo de conexão + subscrição (com plano)

Sequência
1. POST /connect/token  (grant_type=client_credentials)
   → access_token COM claims: pnt_plan, pnt_symbols, pnt_book, pnt_tick, pnt_market

2. Conecta ao /mdhub com o token
   → No OnConnectedAsync o servidor:
       • resolve o identificador do cliente (nameidentifier → client_id)
       • faz o parse do plano (1x) e memoiza
       • lê pnt_book e registra a POLÍTICA DE BOOK do cliente no manager
       • adiciona o cliente ao grupo do tenant

3. SubscribeMarketData(requestId, asset, topic)
   → O servidor aplica os gates NA ORDEM:
       (a) Escopo pntdata_live_scope (allow-list DB + claim scope no JWT)
       (b) Resolve o plano; se SEM plano → caminho legado, retorna
       (c) Gate TICKER   → topic == "Ticker" exige plano advanced-ambos
       (d) Gate TICK     → topic LastTrade/LastTradePrice exige pnt_tick=true
       (e) Gate MERCADO  → o mercado do ativo deve estar em pnt_market
       (f) Gate SÍMBOLOS → checagem atômica do limite (rejeita ANTES de mutar estado)
   → Se algum gate falhar: OnSubscribeMarketDataError(requestId, mensagem)
   → Se todos passarem: subscrição efetivada

4. Recebe OnUpdateMarketData(asset, topic, payload)
   → Book entregue conforme a política do cliente (completo ou só topo)
⚠️
Ponto crítico de latência: o feeder é sempre subscrito na profundidade máxima configurada — a diferença lite/completo acontece na entrega (ver Book lite × advanced), não na subscrição. Isso mantém os gates fora do caminho crítico de cada mensagem.
⚠️
A ordem dos gates importa. Se um pedido violar mais de uma regra, você recebe a mensagem do primeiro gate que falhar (Ticker → Tick → Mercado → Símbolos).

Ciclo de vida da conexão

Quando o cliente chama md.start():

#O servidor faz
1Valida o JWT e extrai o identificador do cliente das claims (nameidentifier ou, na falta, client_id). Sem identificador, a conexão é abortada.
2Faz o parse do plano (1x) e registra a política de book do cliente no manager.
3Registra a conexão no Connection Manager interno.
4Adiciona o cliente a um grupo SignalR específico do tenant ("WebBroker {Tag} Feeder Users").
⚠️
Registre os callbacks (md.on(...)) ANTES de conectar. Eventos que cheguem antes de o handler estar registrado são perdidos.

Reconexão

⚠️
Não há auto-resubscribe após reconexão. Subscrições estão associadas à connectionId, não ao usuário. Após reconectar, chame SubscribeMarketData novamente para todos os tópicos.
JavaScript
md.onreconnected(async () => {
  for (const sub of mySavedSubscriptions) {
    await md.invoke("SubscribeMarketData", crypto.randomUUID(), sub.asset, sub.topic);
  }
});

Quando o cliente desconecta, o servidor faz cleanup automático: remove todas as subscrições de Market Data e OHLC daquela conexão e libera as vagas de símbolo do plano.

Quick Start

Exemplo mínimo: conecta, registra callbacks e subscreve PETR4 em múltiplos tópicos. Book/AggrBook: não envie sufixo de profundidade.

JavaScript
import { HubConnectionBuilder } from "@microsoft/signalr";

const md = new HubConnectionBuilder()
  .withUrl("https://webbrokermdhml.pnt.api.br/mdhub", {
    accessTokenFactory: () => myAccessToken
  })
  .withAutomaticReconnect()
  .build();

// 1. Registre callbacks ANTES de conectar
md.on("OnUpdateMarketData", (asset, topic, payload, serverSendUtcMs) => {
  console.log(`[${asset}/${topic}]`, payload);
});
md.on("OnUpdateSecurityInfo", (relatedSymbols) => console.log("SecurityInfo:", relatedSymbols));
md.on("OnUpdateOptionList", (baseSymbol, optionSymbols) => console.log("Opções:", baseSymbol, optionSymbols));
md.on("OnUpdateOhlcBar", (symbol, type, duration, durationType, bar) => console.log("OHLC:", symbol, bar));
md.on("OnSubscribeMarketDataError", (reqId, msg) => console.error("Erro subscrição:", reqId, msg));
md.on("OnSubscribeMarketDataNotice", (reqId, msg) => console.info("Aviso subscrição:", reqId, msg)); // opcional

Book com profundidade variável (lite × advanced)

Consequência direta do controle de acesso por plano. Regra: o feeder é sempre dirigido na profundidade máxima configurada no servidor. A diferença entre planos acontece na entrega:

Política (pnt_book)O que o cliente recebe
2 (advanced) ou legado (sem plano)Book completo, até o máximo configurado na API (leia MarketDepth).
1 (lite)Apenas o topo de book: 1 bid + 1 offer (MarketDepth=1), independentemente do N pedido.

Internamente, ao enviar um Book2, o servidor particiona os assinantes daquele ativo por política. Quem é pnt_book=1 recebe uma projeção de topo (Book2.ProjectTop1(), que reaproveita as referências do nível 0 — sem cópia profunda); os demais recebem o book completo. Se nenhum assinante for lite, o envio é idêntico ao legado (custo zero).

💡
A entrega do book lite não adiciona latência — pelo contrário, tende a ser mais rápida: ProjectTop1() é O(1) (copia só 2 referências); a projeção é calculada uma vez por update (100 clientes lite compartilham um único envio); o payload menor gera menos serialização e menos bytes na rede; e sem assinante lite o caminho é idêntico ao legado.
⚠️
Implicações para o cliente: não envie sufixo _N (subscreva com "Book"/"AggrBook"); não assuma profundidade fixa — leia MarketDepth e o tamanho de ListBids/ListOffers; um cliente advanced recebe até o máximo da API (que pode ser menor do que esperava); um cliente lite sempre recebe 1 nível de cada lado.

Disponibilidade do Feeder

O WB_MD notifica todos os clientes quando a conexão TCP com um feeder de market data cai e quando se recupera. Use esses eventos para sinalizar ao usuário que os dados podem estar temporariamente paralisados.

OnFeederUnavailable(feederTag)

JavaScript
md.on("OnFeederUnavailable", (feederTag) => {
  // Suspenda a expectativa de updates para as subscrições afetadas.
});

Broadcast quando um feeder desconecta. feederTag identifica o feeder afetado.

OnFeederRecovered(feederTag, pendingSubscriptions)

JavaScript
md.on("OnFeederRecovered", (feederTag, pendingSubscriptions) => {
  // pendingSubscriptions = nº de resubscrições reexecutadas pelo servidor.
});

Broadcast quando o feeder reconecta. pendingSubscriptions é a quantidade de resubscrições que o servidor está reproduzindo automaticamente.

💡
O servidor reproduz as subscrições pendentes ao reconectar o feeder — o cliente não precisa resubscrever por conta de um OnFeederUnavailable/OnFeederRecovered (diferente da reconexão do próprio cliente SignalR, que exige resubscrição — ver Reconexão).

Boas Práticas

✅
Registre os callbacks ANTES de start() — mensagens enviadas antes do handler existir são descartadas.
✅
Use withAutomaticReconnect() e implemente onreconnected para resubscrever — o servidor não preserva subscrições após reconexão do cliente.
✅
Renove o token proativamente — não espere o 401.
✅
Não envie sufixo _N em Book/AggrBook e leia MarketDepth nos payloads de book — a profundidade é definida pela API, nunca a assuma.
✅
Gerencie sua contagem de símbolos — com plano, trate Symbol limit reached dessubscrevendo antes de subscrever novos.
✅
Trate OnFeederUnavailable como sinal operacional — alerte o usuário de que os dados estão paralisados.

Strategy Robot — Envio de Estratégias

O Strategy Robot (WebBroker) é o hub SignalR pelo qual o cliente envia, modifica, cancela e acompanha estratégias algorítmicas (TWAP, VWAP, SwingTrade, SpreadMaker, SpreadMultiLeg, Auction, OnSchedule, Sniper) e, opcionalmente, roteia ordens diretas ao OMS.

O hub usa WebSocket como transporte (HTTP long-polling não é suportado), exige autenticação OAuth2 Bearer (JWT) emitido pelo mesmo Authorization Server da Plug n' Trade já descrito em Autenticação, e comunica-se em JSON sobre o protocolo SignalR.

Quick Start em JavaScript

Exemplo mínimo (≈20 linhas) que conecta, subscreve eventos e envia uma estratégia SwingTrade:

JavaScript
import { HubConnectionBuilder, LogLevel } from "@microsoft/signalr";

const connection = new HubConnectionBuilder()
  .withUrl("https://webbrokerhml.plugntrade.com.br:8080/Robot/robothub", {
    accessTokenFactory: () => myAccessToken
  })
  .withAutomaticReconnect()
  .configureLogging(LogLevel.Information)
  .build();

// 1. Registre os callbacks ANTES de conectar
connection.on("OnGetSnapshot", (json) => {
  const strategies = JSON.parse(json);
  console.log("Snapshot inicial:", strategies);
});
connection.on("OnCurrentUserStrategies", (json, accountNumber) => {
  const strategy = JSON.parse(json);
  console.log("Atualização:", strategy.StrategyId, strategy.StrategyStatus);
});
connection.on("OnSetStrategyParamsError", (reqId, msg) => {
  console.error("Erro de envio:", reqId, msg);
});

// 2. Conecte
await connection.start();

// 3. Subscreva eventos (recebe snapshot + atualizações)
const subId = crypto.randomUUID();
await connection.invoke("SubscribeEventsForAllStrategies", subId);

// 4. Envie uma estratégia
const reqId = crypto.randomUUID();
const strategy = {
  TargetStrategy: "2028",            // SwingTrade
  Side: "C",
  Symbol: "PETR3",
  OrderQty: 5000,
  PriceLimit: 44.0,
  PriceLimit2: 44.5,
  PriceStartGain: 44.5,
  PriceSendOrderGain: 44.2,
  PriceStopLoss: 42.85,
  PriceSendOrderLoss: 42.85,
  MaxLeftPercent: 50,
  FollowProclaim: true,
  StartTime: "2025-06-03T10:00:00",
  EndTime:   "2025-06-03T18:55:00",
  AccountNumber: "502",
  BVSPAccount:   "502",
  BMFAccount:    "502"
};
await connection.invoke("SendStrategyToRobot", reqId, strategy);

A partir daí, as atualizações chegam pelo callback OnCurrentUserStrategies enquanto a estratégia estiver viva.

Resolução dinâmica de URL

O JWT emitido pelo Authorization Server pode conter um claim customizado chamado WB. Quando presente, ele indica o hostname do WebBroker que serve aquele cliente (cada corretora tem seu próprio backend). A URL final é montada como:

URL
https://<valor_do_claim_WB>/Robot/RobotHub

Se o claim não existir, use a URL canônica acima. Implementações de cliente típicas decodificam o JWT, leem o claim e ajustam a URL antes de conectar.

Ciclo de vida da conexão

Quando o cliente chama connection.start():

#O servidor faz
1Valida o JWT.
2Extrai claims do token: usernameinthebroker, broker, grant_type, scope.
3Se grant_type == "client_credentials": o servidor consulta o OMSDB para validar que o client_id tem conta linkada e permissões. Sem isso, a conexão é fechada com OnConnectionError.
4Inicializa o estado do usuário no robô (mapa de contas, advisor access, etc.).
5A conexão fica pronta para invocações.
⚠️
Antes de invocar qualquer método, registre os callbacks (connection.on(...)). Eventos que cheguem antes de o handler estar registrado são perdidos.

Reconexão automática

⚠️
Use sempre withAutomaticReconnect(). Em desconexões transitórias, a biblioteca SignalR reconecta sozinha e o accessTokenFactory é re-invocado para obter um token novo (caso o anterior tenha expirado). Subscrições não são preservadas após reconexão completa — após connection.onreconnected(...), chame SubscribeEventsForAllStrategies novamente.

Autorização de risco (Gênio)

ℹ️
Módulo dependente da corretora. O Gênio é um gate de risco que nem toda corretora contrata. Onde ele não está ativo, nada nesta seção acontece: a estratégia segue direto para o robô e os códigos AUTH-x nunca aparecem. Confirme com a corretora se o módulo está ativo antes de implementar o tratamento descrito aqui.

Onde o módulo está ativo, toda ordem nova e toda edição passam pelo gate antes de chegar ao robô. O gate é fail-closed: sem autorização, a requisição não é transmitida.

O fluxo acrescenta um estado transitório ao ciclo de vida da estratégia:

envio → PendingAuth → autorizado → segue para o robô → não autorizado → Rejected

Enquanto a estratégia está em PendingAuth, ela já aparece em OnCurrentUserStrategies, com esse status. Trate-a como pendente, não como ativa: ela ainda pode ser rejeitada.

O resultado chega no campo de mensagem da estratégia, sempre prefixado por um código entre colchetes:

CódigoSituaçãoO que significa para o cliente
[AUTH-3]Autorização pedida, aguardando respostaEstado transitório. Aguarde.
[AUTH-4]Autorização aceita, requisição enviada ao robôCaminho feliz. A estratégia segue o ciclo normal.
[AUTH-5]Erro ao solicitar autorizaçãoA requisição não foi enviada. Pode reenviar.
[AUTH-6]Requisição enviada ao robô, autorização falhou mas foi enfileiradaA requisição foi enviada; a autorização será conciliada depois. Não reenvie.
[AUTH-7 / XP-GEN01]Limite do perfil excedidoRejeitada por risco. O perfil de investidor precisa ser revisto — a mensagem traz o caminho para isso.
[AUTH-8]Estratégia não autorizada para envio por esta plataformaO tipo de estratégia está bloqueado por configuração. Reenviar não adianta.

Tratamento de Erros — Camadas

Erros podem ocorrer em várias camadas — entender em qual delas seu erro está ajuda a diagnosticar e tratar corretamente.

CamadaSintomaAção recomendada
Transporte (HTTP/WebSocket)Falha na chamada start(), status 401/403/500.Verificar URL, conectividade, certificado, JWT válido. Reaplicar com token novo.
Autenticação (JWT)HTTP 401 ao conectar.Token expirado, assinatura inválida, issuer/audience errado. Renovar token.
Conexão (conta/permissão)OnConnectionError logo após conectar.Cliente sem conta/permissão na corretora. Corrigir o setup do client_id.
Autorização (escopo)Conexão estabelece, mas chamada retorna OnAuthorizationError.Token não tem o escopo robot_signalr_api. Solicitar token com escopo correto.
Validação de parâmetrosRobotHubResponse.Success: false, ou OnSetStrategyParamsError.JSON inválido, campo obrigatório faltando, valor fora do range. Corrigir e reenviar.
Execução / mercadoEstratégia entra em Rejected ou Canceled com ErrorDescription.Falha na bolsa (papel suspenso, túnel violado, conta sem permissão). Ler ErrorDescription.
CallbackCamadaO que fazer
OnConnectionErrorConexãoCliente não tem conta/permissão. Não tente reconectar — corrija o setup do client_id.

Boas Práticas

✅
Sempre registre os callbacks ANTES de start() — mensagens enviadas pelo servidor antes do handler estar registrado são descartadas.
✅
Use withAutomaticReconnect() e implemente o handler onreconnected para re-subscrever os eventos de estratégias (o servidor não preserva subscrições após reconexão).
✅
Renove o token proativamente — não espere o 401. A 50 min de uso (token de 1 h), peça um novo e atualize a referência usada pelo accessTokenFactory.
✅
Idempotência de envio — se você não tem certeza se o SendStrategyToRobot chegou ao servidor (timeout), não reenvie cegamente. Reuse o mesmo ClOrdId para que o servidor faça deduplicação.
✅
Trate OnRobotDown como sinal operacional — quando o robô da corretora cai, suas estratégias não estão executando; alerte o usuário.

OHLC Histórico — PnT Data Hist API

O PnT Data Hist é o serviço de dados OHLC (candles) históricos da plataforma Plug n' Trade. Ele fornece acesso programático a dados de mercado da B3 — Bovespa (ações) e BMF (futuros) — com granularidade de 1 minuto até 1 dia, para uso em backtests, robôs e aplicações server-to-server.

Diferente do capítulo OHLC — Velas em Tempo Real (push via SignalR, sem lookback), este serviço é uma API REST própria para consulta de candles já fechados em qualquer período disponível no InfluxDB. O serviço foi projetado como infraestrutura enterprise: autenticado, controlado por plano, protegido contra sobrecarga e com cache inteligente — de forma que nenhum cliente individual possa degradar o serviço para os demais.

Proteção e Resiliência

Circuit breaker do InfluxDB

Implementado com Polly. Abre quando:

CondiçãoJanela
Erros/timeouts > 5%2 minutos
p95 de influx_query_ms > 5.000ms2 minutos

Após abrir: rejeita queries com HTTP 503 influx_circuit_open. Fecha novamente após: cooldown de 30 segundos (configurável).

GlobalInfluxGuard

Semáforo Redis que limita globalmente a 6 queries simultâneas no InfluxDB. Protege o banco independente do volume de clientes ativos. Requests que excedem o semáforo recebem HTTP 503 service_unavailable.

Warmup queue

Fila Redis (pntdata:warm:q) para pre-warming assíncrono de segmentos de cache. Um worker em background consome a fila e pré-aquece chunks mais prováveis de serem solicitados, reduzindo cache misses nos horários de pico.

Configuração: Warmup.WorkerConcurrency = 2, MaxQueueDepthSoft = 20.000.

Compressão de resposta

Brotli e GZip habilitados por padrão para respostas application/json. Reduz significativamente o payload em requests com muitos candles.
